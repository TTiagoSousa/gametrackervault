# 17 · Android app

A native Android app (`apps/android`) that opens GameTracker Vault from the user's server
in a WebView, full screen and with its own icon. It doesn't carry the interface inside
the APK: it connects to the server the user picks on first launch and shows the site from
there. The APK is built with `npm run build:android`, goes into git together with the
frontend and is served by the site itself at `/downloads/`. From 1.1.0 the app updates
itself from that APK (see [Updating the app](#updating-the-app-updater)).

**Status:** built and with the signature verified (`apksigner verify`, `aapt2 dump`),
but **not yet tested on a phone or an emulator** — nor the automatic update.

---

## Why a WebView connected to the server

The alternative would be to package the frontend build in the APK (Capacitor or
similar). It wasn't done that way because:

- **It's always up to date.** The interface comes from the server: when the admin updates
  the installation (Admin → Version), the app shows the new version straight away. The
  APK only changes when the shell itself changes — so it has its own version, independent
  of the server releases.
- **The same login.** The pages come from the server, on the same origin as the API
  (`/api`), so the httpOnly `access_token` cookie works just like in the browser — no
  tokens anywhere else, no backend changes.
- **No CORS.** A frontend inside the APK would be another origin (`file://` or
  `https://localhost`); it would have to go into `FRONTEND_URL`, the `sameSite: strict`
  cookie wouldn't travel and the login would have to switch to a token. This way nothing
  changes.
- **Size.** No AndroidX or libraries: one Activity and the `Updater` in Java, two local
  HTML pages and a vector icon. The APK is ~27 KB.

The cost: without a connection to the server the app shows nothing beyond the "No
connection" screen.

## How it works (`MainActivity`)

An `Activity` with a `FrameLayout` and a `WebView`, both with the `#0D1230` background
(no white flash while the page loads).

- **WebView:** JavaScript and DOM storage enabled; `setSupportMultipleWindows(false)`, so
  `target="_blank"` links open in the same view and go through the same navigation rule
  as the others. Cookies accepted (`CookieManager`).
- **User agent:** the system one plus ` GameTrackerVaultApp/<version> (Android)`. That's
  how the frontend knows it's inside the app (`isAndroidApp()`).
- **Edge-to-edge (Android 15):** with `targetSdk` 35 the system draws the app behind the
  bars. An `OnApplyWindowInsetsListener` on the `FrameLayout` applies the system bars,
  the camera cutout and the keyboard (`ime`) as padding — the site always stays between
  them. The manifest also has `adjustResize`.
- **State:** `onSaveInstanceState` / `restoreState` keep the WebView history if Android
  kills the Activity; `onPause` calls `CookieManager.flush()`, so the session survives a
  force close.
- **Back:** Android's Back button calls `webView.goBack()` while there's history and the
  page isn't one of the local ones; otherwise it exits the app.
- **http on the home network:** `usesCleartextTraffic="true"` allows an
  `http://192.168.x.x` address, not just the https domain.

The server is stored in `SharedPreferences` (`gametracker` → `server_url`), already
normalized, without a trailing slash.

### Navigation

`shouldOverrideUrlLoading` decides where each link opens:

| Destination | Where it opens |
|---|---|
| `file://` (the local pages) | in the WebView |
| `http(s)` with the **same host** as the saved server | in the WebView |
| everything else (other sites, `mailto:`, `intent:`…) | outside the app, with `Intent.ACTION_VIEW` (browser or the right app); with no app to open it, nothing happens |

The comparison is by host only: another port or scheme on the same host stays in the
app. IGDB, YouTube, Twitch or Anthropic console links open in the browser.

### Load errors

`onReceivedError` only reacts to **main page** errors (`isForMainFrame`) that aren't
local pages: it loads `offline.html`. A failing image or API request doesn't cover the
app — the site handles those itself.

## Flows

### First launch

```
MainActivity.onCreate → openStart()
    no server_url → file:///android_asset/setup.html
        texts in the phone's language (navigator.language: pt · es · rest → en)
        user types the address → "Connect"
            window.GameTrackerApp.connect(text)
                (only accepted if the current page is local — see The bridge)
                normalize: trims, no scheme → "https://", strips trailing slashes,
                           no host → "invalid"
                check (on a thread, 8 s timeouts):
                    GET <server>/api/health   (CT installation: nginx → backend)
                    GET <server>/health       (backend directly)
                    200 with { app: "gametracker-vault" } → "ok"
                    answered, but not that              → "not-gametracker"
                    no answer                           → "unreachable"
            "ok"   → saves server_url, clears history, opens <server>/
            other  → window.onConnectResult(code) → message in the form
    <server>/ → the normal site → login (httpOnly cookie, as in the browser)
```

### Later launches

```
openStart() → saved server_url → loadUrl(<server>/)
    the CookieManager cookie is still valid → the site opens already signed in
        AuthProvider → GET /api/auth/me
            401               → login
            network failure/5xx → tries twice more (1.5 s, 3 s) before giving up
```

The retries in `Auth_Context.refreshUser` exist because of the app: when the phone wakes
up the network can take a moment, and before that any error showed the login to someone
with a valid session.

### No connection

```
error on the main page → offline.html  ("No connection to the server", shows the address)
    "Try again"      → GameTrackerApp.retry()        → openStart()
    "Change server"  → GameTrackerApp.changeServer() → forgets the server → setup.html
```

### Change server

Three paths, all to `GameTrackerApp.changeServer()`: the "No connection" screen, the
`Top_Nav` account menu (inside the app, "Change server" replaces "Android app") and the
"Change server" link on the `Android_Download` card in Help. It deletes `server_url`,
clears the history and opens `setup.html`. The field comes pre-filled with the previous
server: when connecting, the app also saves `last_server_url`, which `currentServer()`
returns when there's no saved server any more. The old server's session cookie stays in
the `CookieManager`.

### Updating the app (`Updater`)

The app's content always follows the server; the APK has a separate version and only
changes when the shell changes (see [Versions](#versions)). For that case, since 1.1.0
the app checks for and installs the APK published by the server itself, without going
through the browser.

```
MainActivity.onCreate → updater.check(server_url, automatic)
connect(...) with "ok" → updater.check(new server, automatic)
Help → "Update app" / "Check for updates" → GameTrackerApp.checkUpdate()
                       → updater.check(server_url, manual)

check (on a thread)
    automatic: only once per launch (askedThisRun) — "Later" holds until the app
               is closed; with no new version or no answer, it says nothing
    GET <server>/downloads/android.json   (8 s timeouts, no cache)
        versionCode > BuildConfig.VERSION_CODE → "New app version" dialog
                                                 "Update" · "Later"
        equal or lower (manual only)           → "You already have the latest version (x.y.z)."
        error, non-200 or no versionCode       → (manual only) "Couldn't check for
                                                 updates…"

"Update"
    dialog with a progress bar (can't be dismissed)
    PackageInstaller: MODE_FULL_INSTALL session, setAppPackageName, setSize
        Android 12+: setRequireUserAction(USER_ACTION_NOT_REQUIRED)
    GET <server>/downloads/gametracker-vault.apk → written into the session ("base.apk"),
        with the sha256 computed along the way
    sha256 ≠ the info file's → abandons the session → "The downloaded file is damaged."
    correct → commit with a broadcast PendingIntent (FLAG_MUTABLE on Android 12+)

receiver (registered in the Activity; RECEIVER_NOT_EXPORTED on Android 13+)
    STATUS_PENDING_USER_ACTION → opens the system confirmation screen
    STATUS_SUCCESS             → Android replaces (and closes) the app
    STATUS_FAILURE_ABORTED     → nothing (the user cancelled)
    other                      → "Couldn't update: <reason>"
```

- **Confirmation.** The first time, Android asks to allow installing apps from
  GameTracker Vault (the `REQUEST_INSTALL_PACKAGES` permission only allows asking) and
  then confirms the installation. On Android 12+, once this app becomes the installer of
  the current version (that is, after the first update done by it), later ones can
  install without asking.
- **Signature.** Android only accepts the new APK if it's signed with the same key (see
  [below](#npm-run-buildandroid)); the info file's sha256 catches downloads that were cut
  short or swapped along the way.
- **Texts** in `res/values*/strings.xml` (`update_*`): English by default, `values-pt`
  and `values-es`, by the phone's language — not by the language chosen on the site.
- **1.0.0 has no `Updater`.** Whoever has it installs 1.1.0 by hand once (download and
  install over it); from then on the app updates itself.
- `onDestroy` unregisters the receiver (`updater.release()`).

## The bridge (`window.GameTrackerApp`)

`addJavascriptInterface(new Bridge(), "GameTrackerApp")`. Only methods with
`@JavascriptInterface` are visible:

| Method | Used by | What it does |
|---|---|---|
| `connect(address)` | `setup.html` | normalizes, checks `/api/health` · `/health`, saves and opens; or answers through `window.onConnectResult(code)` |
| `retry()` | `offline.html` | reopens the saved server (or `setup.html`) |
| `changeServer()` | `offline.html`, `Top_Nav`, `Android_Download` | forgets the server and opens `setup.html` |
| `currentServer()` | `setup.html`, `offline.html` | the saved server, otherwise the last one used (`last_server_url`), otherwise `""` |
| `version()` | `Android_Download` | `BuildConfig.VERSION_NAME` |
| `versionCode()` | `Android_Download` | `BuildConfig.VERSION_CODE`, to compare with the `versionCode` in `android.json` (since 1.1.0) |
| `checkUpdate()` | `Android_Download` | checks for a new version (manual) and always reports the result: offers the update, "you already have the latest version" or "couldn't check" (since 1.1.0) |

In the frontend, `Service/androidApp.ts` declares the type (`changeServer`, `version`
and, as optional, `versionCode` and `checkUpdate` — a 1.0.0 app doesn't have them) and
`androidBridge()` returns the bridge only when the user agent contains
`GameTrackerVaultApp`.

**Security rule.** The bridge is injected into every WebView page — which, by the
navigation rule, can only be the local ones and those of the saved server. Even so,
`connect` **is only accepted when the current page is local**
(`file:///android_asset/…`, checked on the UI thread): no server page (nor a script
injected into it) can point the app at another server without the user typing it.
`changeServer` can come from the site — it's what the account menu uses — but it only
forgets the server; the new one always has to be typed by hand. The result returned to
`onConnectResult` is one of three fixed codes, never text from outside. `checkUpdate` can
also come from the site, but it only checks the already saved server, and the
installation always goes through the app's dialog and Android's signature verification.

## Build, sign and publish

### Requirements (only on the building machine)

- **JDK 17+.** The script looks for `JAVA_HOME` and then Microsoft, Temurin or Oracle
  JDKs in the usual folders (Windows: `C:\Program Files\Microsoft|Eclipse Adoptium|Java`;
  Linux/macOS: `/usr/lib/jvm`, `/Library/Java/JavaVirtualMachines`). On this machine:
  Microsoft OpenJDK 21 (`winget install Microsoft.OpenJDK.21`).
- **Android SDK** with `platforms;android-35` and `build-tools;35.0.0`. The script uses
  `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `%LOCALAPPDATA%\Android\Sdk` or `~/Android/Sdk`
  (`~/Library/Android/sdk` on macOS) — the first folder that has `platforms/`. On this
  machine: the command-line tools in `%LOCALAPPDATA%\Android\Sdk`, installed with the new
  CLI (`android sdk install`); Gradle also fetched `build-tools;34` and the
  `platform-tools`.
- On the first build Gradle downloads itself (8.11.1) and the AGP.

The CT needs none of this: it receives the ready-made APK, in git.

### `npm run build:android`

`scripts/build-android.mjs`, at the root:

1. Finds the JDK and the SDK (fails with a message saying what to install).
2. Writes `apps/android/local.properties` (`sdk.dir=…`, outside git).
3. The first time, creates the signing key **outside the repository**, in
   `~/.gametracker/` (or `GAMETRACKER_KEYSTORE_DIR`): `android-release.jks` (RSA 4096,
   100-year validity, alias `gametracker`) and `android-keystore.properties` (path and
   random password). If the `.jks` exists without the `.properties`, it stops and asks
   for it to be restored from backup.
4. Bumps the version in `apps/android/gradle.properties` (see [Versions](#versions)).
5. Runs `gradlew assembleRelease` in `apps/android`, with `JAVA_HOME` and
   `GAMETRACKER_KEYSTORE_PROPERTIES` pointing to the properties file — that's where
   `app/build.gradle` reads the signing config from. Without it the APK would come out
   unsigned. If the build fails, `gradle.properties` goes back to what it was.
6. Copies the APK to `apps/frontend/public/downloads/gametracker-vault.apk` and writes
   `android.json` next to it (the new version and `versionCode`, size, sha256, date).

| Command | Version |
|---|---|
| `npm run build:android` | `versionCode` +1 and the last version number +1 (1.1.0 → 1.1.1) |
| `npm run build:android -- --version 1.2.0` | sets that version (must be `x.y.z`); `versionCode` +1 |
| `npm run build:android -- --keep-version` | changes neither (e.g. re-signing) |

The APK is signed with the v2 scheme (with `minSdk` 26, v1 isn't needed).

> **Keep the `~/.gametracker/` folder.** Android only accepts updating an app with an APK
> signed by the same key. Without `android-release.jks` and the password, a new APK won't
> install over the old one: every phone would have to uninstall the app (losing the saved
> server and the session) and install it again. The key never goes into git (`*.jks`,
> `*.keystore` and `keystore.properties` are in the `apps/android` `.gitignore`).

### Versions

The app has its own version, in `apps/android/gradle.properties`:

```properties
APP_VERSION_NAME=1.1.0
APP_VERSION_CODE=2
```

It doesn't track the server releases — the interface always comes from the server, so
there's only a new APK when the shell changes (`MainActivity`, `Updater`, local pages,
icon, manifest). `APP_VERSION_CODE` must go up with every published APK: with the same
code (or lower) Android refuses to install over it, and it's what installed apps compare
to offer the update. **It's no longer bumped by hand**: `npm run build:android` bumps it
on every build (table above). Only `--keep-version` produces an APK with the same code —
it's for re-signing, not for publishing a new version.

History: 1.0.0 (`versionCode` 1) — the first, without automatic updates; 1.1.0
(`versionCode` 2) — the `Updater`.

### Publishing a new app version

1. Change whatever is needed in `apps/android`.
2. `npm run build:android` (or `-- --version x.y.z` for a version that isn't just the
   last number).
3. Commit the code, `gradle.properties` **and** the APK and `android.json` in
   `apps/frontend/public/downloads/` (e.g. `feat(android): …`).
4. Follow the normal flow: `develop` → `staging` → `main`, release (see
   [15](./15-deploy-and-environment.md)). When the CT updates, the frontend build copies
   `public/downloads/` to `/var/www/gametracker/downloads/`, and nginx serves it without
   cache.
5. On phones with 1.1.0 or newer: on opening, the app asks **Update / Later** (or Help →
   Android app → **Update app**). With 1.0.0: Help → Android app → download the APK in
   the browser and install over it, once.

## In the frontend

- **Help** — the first section is `android` (`help:android.*`): install, first time, day
  to day. Above the text, the `Android_Download` card reads `/downloads/android.json` and
  shows version, size, date and the **Download APK** button; without the info file
  (installation without an APK) it says it's not available and disables the button.
  Inside the app it shows "You are using the Android app" and the installed version — or,
  if `android.json` has a `versionCode` greater than the bridge's `versionCode()`, "You
  have version X — Y is out" — and the **Update app** button (when there's a new version)
  or **Check for updates**, both calling `checkUpdate()`. In a 1.0.0 app (no
  `checkUpdate`) with a new version available it shows a download link instead. The
  section text has "Updating the app".
- **Account menu** (`Top_Nav`) — in the browser, "Android app" goes to
  `/Vault/Help#android`; inside the app, "Change server" calls `changeServer()`.
- **Phone layout** — the app has no layout of its own: it shows the site, and on a phone
  (less than 760px wide) the site already uses the phone layout — a 56px top bar with
  only brand, theme and avatar, `Bottom_Nav` fixed at the bottom with the five sections,
  Admin in the avatar menu and, on a game page, "My shelf" in a sheet that slides up from
  the bottom (see [10](./10-frontend-pages.md#bottom_nav) and
  [11](./11-design-system.md#mobile)). Nothing depends on `isAndroidApp()`: it's the same
  in the phone's browser. Since `MainActivity` already applies the system bars as
  padding, `env(safe-area-inset-bottom)` inside the WebView should be 0 — the bottom bar
  stays at 62px, above the gesture bar and not behind it. Not yet seen on a device.

## Limitations

- **Only against an installation with nginx.** The app needs the site and the API on the
  same origin (`/` and `/api`). In development the frontend (5190) and the backend (3200)
  are on different ports and the frontend calls `localhost:3200` — on the phone,
  `localhost` is the phone itself. To test, point the app at the CT.
- **No connection, nothing.** There's no offline cache or service worker: without a
  server only the "No connection" screen appears.
- **No `WebChromeClient` or `DownloadListener`.** Picking files (`<input type="file">`),
  fullscreen video, JavaScript dialogs and downloading files inside the WebView aren't
  wired up. Today the site barely uses any of them; a new feature that needs them has to
  add them in `MainActivity`. That's why the download link the Help card shows to a 1.0.0
  app with a new version available points to the APK on GitHub
  (`ANDROID_APK_REPO_URL`): it's another host, so the app opens it in the phone's
  browser, which downloads it.
- **1.0.0 doesn't update itself.** Whoever has it installs 1.1.0 by hand once; only from
  then on is updating automatic.
- **Updates follow the saved server.** The app only checks for new APKs on the server it's
  connected to; if that server hasn't been updated yet (the new APK arrives with the
  server release), the app doesn't see the new version.
- **Installed outside the Play Store.** Android warns that it's from an unknown source
  and asks to authorize the browser or the file manager — and, for automatic updates, the
  app itself (once).
- **One server at a time.** Changing server forgets the previous one; its cookie stays
  stored.
- **APK in git.** Each new version adds a binary (~27 KB) to the history.
- **Every build is a version.** `npm run build:android` always bumps the version (except
  with `--keep-version`): building several times before publishing skips numbers. That's
  fine — it only has to go up — but commit `gradle.properties` together with the APK.
